## 0. いま何を決めようとしているか（テーマ）

「常時可視化ダッシュボード」から「**全社が使う業務ハブ**」への本格化。具体的な検討対象は3つ：

1. **締切（目標期日）の導入** — 時間軸を持たせ、仕事を管理しやすく
2. **削除／アーカイブ** — ダッシュボードからのレコードのライフサイクル
3. **データモデルの再設計** — 複数シート → 統合（現況＋ログの2面）

> いずれもドクトリン（思想）に関わるため、コード実装の前に「設計判断」を固める。

## 1. 締切（deadline）

### 暫定方針（壁打ちでの leaning。未確定）
- **入れる価値は高い。§1.6（出社の比喩＝便利だから自然に使う）の延長として正しい。**
- 核：締切は「**助け（self-management）**」であって「**鞭（監視・ノルマ）**」にしない。鞭に見えた瞬間、人はツールから逃げる＝逃げ場のなさが逆に壊れる。
- 「**2つの圧**」モデルで核を再定義：
  - **過去の圧＝停滞**（更新日が古い＝動いてない）
  - **未来の圧＝締切**（あと N 日／超過）
  - 交差（停滞×超過）を最優先で炙り出す。

### 未決の問い
1. 締切の**意味**は「Mission を終える**目安日（target）1種類**」で始める？（硬い期日と柔らかい目標の2種は後回し？）
2. 持たせる**層**は？（案：Mission を芯に。Issue は粗いので任意、Task も任意。「Mission 必須／他任意」か「全層任意」か）
3. **入力者**は？（案：DRI 本人が置く＝自分の段取り。事務局は催促で上書き提案＝§1B）
4. 腐敗対策（先に決める）：締切インフレ／死んだ締切（超過放置）→「超過したら再設定 or 結案を促す」運用儀式。

## 2. 削除／アーカイブ

### 暫定方針（leaning。未確定）
- **正常な店じまい＝アーカイブ（履歴を全部残す）／削除＝誤登録の取り消しだけの例外。**
- 理由：核は §3「逃げ場のなさ」。「終わったから消す」を削除でやれると Issue を消して逃げられる＝核が壊れる。
- **アーカイブ＝基本動線**。§1.6 で既に半分決定（`結案/凍結/中止` は既定で畳むが振り返れる）。これを正式に "封存（アーカイブ）" と位置づける。
  - 実装案 A（軽・推奨）：状態ベース。閉状態にした行を active から隠し「封存ビュー」で振り返る。データは動かさない。
  - 実装案 B（重）：別シート `封存` へ退避。メインは軽くなるが親編號参照・復元・カスケードが面倒。→ 量が増えてから。
- **削除＝例外**：
  - **ソフト削除推奨**（`ゴミ箱` シートへ退避してから本表から消す）。§1.5「回収可能なログ」を守る。
  - **削除UIは管理者專用ページ内に隠す**（一般に見せない＝抜け穴を作らない）。本人認証は次フェーズ。
  - **親に生きた子がある削除はブロック**（誤爆防止）。または強い確認でカスケード。

## 3. データモデル再設計（2面構成）

### 暫定方針（leaning。未確定）
- **重要な分離：「現況（上書き・1レコード1行）」と「履歴（追記専用・多行）」は別の面。**
  - 現況：名称/DRI/協作/戰略支援/リンク/定義/狀態/進度現況/目標期日/備考 …
  - 履歴（イベントログ）：**いつ・誰が・何を**（事件＝登録/修正/進度/期日変更/封存/削除）
  - 「初回登録日・登録者」「更新日・改修者」は**履歴から導出して現況にミラー**（常時表示可）。
- **「1枚に統合」への答え：現況は1枚に統合○（I/M/T を `層級` 列で判別）／ログは別の1枚**。完全1枚は現況(上書き)とログ(追記)が混ざり破綻するので不可。
- **6タブ → 「①統合現況」＋「②統合イベントログ」＋ 補助（人員/公告/個人備註）に集約。**
- **編號は不変。版管理はログ側**（編號に修正枝番を持たせない。親子参照・既存リンク・記憶がズレるため）。編號＝不変の住所／ログ＝そこで起きた出来事の連なり。
- 「誰が」には本人識別が要る → 当面は名前選択、本物の認証は次フェーズ（暫定と明記）。

### たたき台スキーマ
**① 統合現況テーブル（1レコード1行）**
```
編號 | 層級(I/M/T) | 親編號 | 名稱 | DRI | 協作 | 戰略支援 |
連結(複数 名前|URL改行) | 定義 | 狀態(7段) | 進度現況 | 目標期日 |
備註 | 建立日 | 建立者 | 更新日 | 更新者 | 封存(狀態 or flag)
```
**② 統合イベントログ（追記専用）**
```
編號 | 層級 | 日時 | 記錄者 | 事件(登録/修正/進度/期日/封存/解封/刪除) |
對象欄位 | 內容(値 または 旧→新)
```

## 3.5 共有パーマリンク／双方向連携（新テーマ）

### やりたいこと
- Mission/Task のモーダルから、**最新情報が集約されたページの URL（パーマリンク）**を発行。
- そのURLを**他人へ送付／Confluence ページへ貼り付け**でき、**IMT ⇄ Confluence の双方向**でアクセスできる。

### 暫定方針（leaning。未確定）
- **編號ベースのディープリンクが本命**：`…netlify.app/#/m/<編號>`（例 `#/m/I001-M1`）。開くと該当レコードの**集約ビュー**（名称/定義/DRI・協作・戰略支援/狀態/**現在進度＋進度タイムライン全文**/全リンク/目標期日/日付）を表示。データはシートから毎回読むので**常に最新**。
- モーダルに「**🔗 連結をコピー**」＝パーマリンクをクリップボードへ。送付・貼付はこれだけ。
- **双方向**：レコードの「連結」列に Confluence URL（既に複数対応）／ Confluence 側に IMT パーマリンク。相互に飛べる。
- 段階：**①ディープリンク（最短・新規ページ生成不要）→ ②専用の軽量ビューページ `view.html?id=`（共有特化・iframe埋込可）→ ③Apps Script＋Confluence API で Confluence ページ自動生成・URL書き戻し（ネイティブ統合・重い）**。

### ドクトリン整合
- §2（入口＋進捗パルスの一次記録）を実体化／§6（Confluence＝成果物）と双方向で結ぶ連結組織に／目的B（事務局の転記・共有がリンク1本に化ける）／§4③（Confluence動線を阻害しない）に合致。

### 未決の問い
1. **「最新（生きたレコード）」が主か、「スナップショット（その時点の凍結版）」も要るか**。後者は別途エクスポート/印刷機能。
2. **アクセス権**：今は公開 gviz 読取＝リンクを持つ人は誰でも閲覧可。送付相手の範囲は？機微があれば本人認証（次フェーズ）。
3. **編號不変が大前提**（パーマリンクは編號依存）。→ §3 の「編號は不変・版はログで管理」を**後押し**する（この機能と一直線）。

> メモ：この機能は §3（編號不変＋進度ログ2面）と相互に補強する。バラバラの追加機能ではなく、ハブ化の幹に乗るテーマ。
