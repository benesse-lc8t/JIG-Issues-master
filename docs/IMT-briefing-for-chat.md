> このドキュメントは、**別のチャット（Claude.ai）にそのまま貼り付けて**、IMT というツールの全体像・思想・現在地・今決めたい論点を一度で理解してもらうための自己完結プライマーです。
> 相手のチャットはリポジトリやコードを見られない前提なので、必要な背景はすべてここに書いています。
> **取扱注意（管理者限定）**：本書には社員に公言しない「管理側の本音」を含みます。利用者（台湾スタッフ）には共有しない前提。

## 1. 組織コンテキスト（TBBS）

- 台湾の会社「TBBS」。社内の経営課題（Issue）を全社で回すためのツールが IMT。
- 部門（處）：**經營戰略 / 整合行銷 / 商品事業 / CX計劃 / 資訊事業 / 財務 / 總管理**。
- 経営の階層と責任者（DRI＝Directly Responsible Individual）：
  - **Issue：DRI＝處長クラス**
  - **Mission：DRI＝組長クラス**
  - **Task：DRI＝組員**
  - 基盤部門は本質的に協作（コラボレーター）として層・部門を跨ぐ。
- **事務局（経営戦略組）＝王詩雅（詩雅）・育菱**。会社全体の Issue/Mission を管理し、催促・方向づけを担う。
- **総経理**＝Issue の起動者（経営の最上位）。
- **小沼（管理者・日本語話者）**＝このツールの設計・運用責任者。リポジトリ閲覧権限は小沼のみ。

## 2. ツールの目的（一行）

**「結果を報告させる会議」から「進捗を見ながら方向をアジャストする会議」へ転換する、Issue/Mission/Task の常時可視化＆業務管理ハブ。**

### 二重の目的
- **(A) 経営幹部が Issue から逃げない構造をつくる**。常時可視化で「向き合うべきテーマから離れられない」状態を維持。
- **(B) 経営戦略組（詩雅・育菱＝事務局）の業務負荷を下げる**。仕事を「転記・代行という作業」から「催促・方向づけ」へ移す。

### 設計の核（社員には公言しない・管理側の本音）
- **Issue を常に・全員の目に晒し続け、各自が自分の向き合うべきテーマから自然に離れられない状態をつくる＝「逃げ場のなさ」を、強制ではなく可視化で実現する。**
- 対外（社員説明・公開ページ）では「進捗共有・方向アジャスト・報告負荷低減」のトーンで語る。「監視」「逃げ場をなくす」等の語は使わない。

## 3. これまでの進化（重要：思想は段階的に上書きされてきた）

1. **初期**：Issue→Task の2層。進捗の実体は Confluence。本ツールは俯瞰図で、**本人入力はゼロ**（可視化だけで逃げ場をなくす）。
2. **路線転換①（本人週次記入＋ログ蓄積）**：本人が週1で進度を**一行・短文**で本ツールに直接記入し、**追記専用ログ**として蓄積。狙いは (a) 回収可能な行ログ (b) **AI に読み込ませるコンテキスト** (c) 事務局の転記消滅。逃げ場のなさは「**書いていない週＝空白が時系列で露呈**」で担保。負荷は「一行固定＋Confluence からの移設」で上げない。
3. **路線転換②（3層カスケード／名前起点プラットフォーム化）**：
   - **Issue→Mission→Task の3層**で全社業務を回すハブへ格上げ。
   - 旧原則「報告負荷を上げない（フィルタ②③）」を**意識的に部分上書き**。新しい歯止めは「**負担だから却下**」ではなく「**使う方が便利だから自然に開く**」（＝出社の比喩。来たくなる場所にする）。ただし記入はストレスゼロ・一行短文中心、重い成果物は Confluence/SharePoint へ**リンク**で逃がす。
   - **状態**：Issue は7状態を付けない（粗く運用、起動者＝総経理）。Mission/Task は **7状態＝構想中 / 策劃中 / 待審核 / 進行中 / 結案 / 凍結 / 中止**。結案/凍結/中止は既定で畳むが振り返れる。
   - **人**：DRI（明示入力）＋複数コラボレーター。
   - **画面は実質2つ**：①管理職＋組員の「**我的（名前起点・自分の仕事一覧）**」②総経理・詩雅・育菱の**俯瞰＋管理**画面。
   - **定義欄**（Issue定義／Mission定義／Task定義）でカスケード健全性（Task⊂Mission⊂Issue の整合）を言語化・可視化。
   - **連携**：賢いリンク集（Confluence / Canva / mindmap / ChatGPT / Claude / Gemini / NotebookLM、365データは SharePoint）。

## 4. 設計判断のフィルター（迷ったらこれで判断する）

1. **常時可視化を強めるか？**（Issue/Task が忘れられにくくなるか）
2. **報告負荷を上げないか？**（※路線転換後は「便利だから自然に使う」へ部分上書き。ただし一行・短文中心、報告フォーム化はしない）
3. **Confluence/成果物への動線を阻害しないか？**（詳細は外部、本ツールは入口＋進捗パルスの一次記録面）
4. **管理者の判断・アジャストを助けるか？**（会議で「どこを掘るか」が見えるか）

## 5. アーキテクチャと現在地（2026-06-02・v0.51.x）

- **静的サイト（index.html 単一ファイル）を Netlify で公開**。データの正は **Google スプレッドシート**（gviz で読取）。書き込みは **Google Apps Script の Web App（doPost）**。管理者用設定は右上「⚙」から。
- 現状のスプレッドシートは複数タブ：`Issue主檔` / `Mission一覽` / `Task一覽` / `Mission進度ログ`（追記専用）/ `人員`（名簿・處カラー）/ `個人備註` / `公告`。
- **直近で大掃除済み**：旧タブ（一覧/会議議程/進度/詩雅/育菱/ダッシュボード）を撤去し、**メイン画面を「我的（My Work）」1枚に集約**。レガシー列も整理。
- **My Work（我的）画面**：名前（DRI）を選ぶと「自分が DRI の行＋その上下層」を表示。検索／顯示全部／僅我DRI／顯示結案／層級トグル。各セルはインライン編集＋モーダル。リロード時は前回の表示状態を復元。
- **見た目のトーン**：人名は「處カラーの小さなドット＋黒文字」（**中華圏の"人名を赤で書く"タブー回避**のため、塗りつぶし色チップ・赤文字は廃止）。狀態は淡色バッジ。起動画面はオーロラ背景＋ロゴ＋一度だけ満ちるバー。
- **認証は未実装**。現状は共有トークン＋「記入者を名前で選択」。本物の本人認証は次フェーズ（静的サイトゆえ厳密なアクセス制御は不可と受容）。

## 6. いま決めたい論点（壁打ちの本題）

### ① 締切（目標期日）の導入
- **入れる方向で確定**。仕事の管理がしやすくなるため。これで IMT は「時間軸を持つ業務管理ハブ」になる。
- 私の暫定 leaning：
  - 締切は「**助け（自分の段取り）**」であって「**鞭（監視・ノルマ）**」にしない。鞭に見えると人はツールから逃げる＝核が壊れる。
  - 「**2つの圧**」で核を再定義：**過去の圧＝停滞（更新が古い）／未来の圧＝締切（あとN日・超過）**。両者の交差を最優先で炙り出す。
- **未決**：(a) 締切の意味は「Mission を終える目安日 1種類」で始める？硬軟2種は後？ (b) どの層に持たせる？（Mission を芯／全層任意？）(c) 入力者は DRI 本人？事務局？ (d) 腐敗対策（締切インフレ・超過放置）の儀式。

### ② 削除／アーカイブ
- 私の暫定 leaning：**正常終了＝アーカイブ（履歴を全部残す）／削除＝誤登録の取り消しだけの例外**。
  - 理由：「終わったから消す」を削除でやれると Issue を消して逃げられる＝逃げ場のなさが壊れる。
  - アーカイブは既存の「結案/凍結/中止（既定で畳む）」を正式に "封存" と位置づけるのが自然。
  - 削除はソフト削除（ゴミ箱へ退避＝回収可能）＋管理者画面に隠す＋親に生きた子があればブロック。
- **未決**：アーカイブは状態ベースか別シート退避か／削除はソフトかハードか／権限／親子の挙動。

### ③ データモデル再設計（2面構成）
- 私の暫定 leaning：**「現況（上書き・1レコード1行）」と「履歴（追記専用イベントログ）」を分離**。
  - 履歴ログは常に **A)いつ B)誰が C)何を**（事件＝登録/修正/進度/期日変更/封存/削除）を残す。AI コンテキストの燃料にもなる。
  - 「初回登録日・登録者／更新日・改修者」は履歴から導出して現況にミラー（常時表示）。
  - **現況は I/M/T を1枚に統合**（層級列で判別）。**ログは別の1枚**。完全1枚は性質が混ざり破綻するので不可。
  - **編號は不変。版管理はログ側**（編號に修正枝番を持たせない）。
- 1レコードが持つ情報（たたき台）：通し番号（親子）/名称/DRI/協作・戰略支援/リンク（複数URL）/初回登録日・登録者/更新日・改修者（アーカイブ・削除も同様）/仕事の定義/現在進度/目標期日/メモ。
- **未決**：2面構成の是非／統合の是非／編號不変＋ログ版管理／ログの事件粒度。
